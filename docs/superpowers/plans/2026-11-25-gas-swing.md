# Bounded Physical Gas Swing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Value and operate daily physical quantity elections with one shared
term minimum/maximum, without losing the existing gas Side and lifecycle contracts.

**Architecture:** A saved gas Instrument owns a swing term over one physical
entry and its following fixed payments. Exact election facts feed each Side's
day quantities. One joint constrained choice calculation supplies the value of
the remaining undecided days; existing Side occurrences supply its economics.

**Tech Stack:** C#/.NET 10, PostgreSQL, TypeScript presentation, Python checks,
existing browser drivers and disposable preview resources.

**Spec:** [Bounded physical gas swing](../specs/2026-11-25-gas-swing-design.md).

**Status:** Proposed task plan, not implemented. All tasks are gated on
[PR #352](https://github.com/zerodrift/leanetrm/pull/352) being merged. The
baseline inspected for this plan was master `cbab62a9`; recheck names and the
merged imbalance changes before starting. The plan's new interfaces are proposed;
existing names below were checked in source.

## Global constraints

- Do not start application, database or browser implementation before #352 merges.
  Base the implementation on the resulting master, preserving this design.
- No option Side, option Instrument, trade created by election or peer-Side access.
  Execute each retained program through its concrete Side.
- First profile: one physical source, 1–31 whole days, fixed payments/fees,
  exact contractual increments and one term-wide volume budget; no count limits.
- Saved choices: model `gas_swing_one_factor_lognormal_v1`, numerical policy
  `swing_trinomial_6h_half_even_18_v1`, quantity policy
  `swing_elected_delivery_quantity_v1`, holders `us`/`counterparty`,
  marks `curve_marks_log_return_held_v1`, time rule
  `lead_before_first_gas_day_v1`, day count
  `OptionNumericalPolicies.ActualOver365FixedInstant`, explicit no discounting.
- Exact quantities and lifecycle amounts. Only model input amounts round half-even
  to 18 decimals; retain `LatticeDecimal` through the joint recursion and call
  `ToExact()` once. Exact deterministic paths remain rational.
- No independent-day call sum, perfect foresight, automatic exercise, missing
  mark fallback, correlation inference or silent numerical-grid changes.
- Keep no-swing canonical identities and all existing expected values unchanged.
  Preserve #352 balance facts, markers, settlement and payment behavior.
- TypeScript presents backend results; no financial calculation or admission there.
- Synthetic fixtures only. TDD on each behavior; signed commits; do not push
  without publication authorization.
- Database/HTTP/browser checks run via `tools/run_preview.py` and
  `tools/check_all.py` with `PG_BIN`, `DOTNET`, `BROWSER` set. Native migrations
  use one transaction, the house advisory lock and every predecessor function pin.
  Use the next free migration and decision numbers at implementation time.

## Review focus

1. A daily-valid election leaves insufficient capacity to meet minimum take;
   reject atomically, including when competing commands touch different days (1, 5).
2. An election is future-effective, later-known, withdrawn, or corrects an
   intermediate historical state; every route uses the same eligible facts (3, 5, 6).
3. Negative mandatory value, last-step exercise and a small stochastic tree;
   neither zero-flooring nor hindsight nor separate calls is correct (2).
4. Two bindings have the same Instrument but different absolute elections;
   no scalar reuse or double application of trade quantity (3, 6).
5. A whole-term payment is part paid before a correction, beside an imbalance
   cash-out and a charge; cash survives and no component is counted twice (3, 6).
